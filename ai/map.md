## `src/index.html`

Page shell: metadata (the viewport meta has `viewport-fit=cover`; two `theme-color` metas, one per
`prefers-color-scheme`, holding the page colour of each theme; the Open Graph and Twitter card
metas with absolute URLs, see "Link preview" below), an inline classic `<script>` in
`<head>` that sets `<html data-theme>` before the first paint (see "Theme" below), favicon
(`favicon.svg`, hashed by Vite), the font preload (`<link rel="preload" as="font" crossorigin>` for `fonts/rubik-latin-wght-normal.woff2`), entry
`<script type="module" src="./scripts/main.js">`, the GitHub link (`.github-link`, first in `<body>`),
the `.game-layout` wrapper — the
header (below), `<main class="game-container">` with the empty `.game-grid` (the
background cells and the tiles are generated by `GridView`) and the `<footer class="site-footer">`
(see "Page: the GitHub link and the footer" below) — and four modal `<dialog>`s: win (`.win-overlay`:
`.win-message`, `.continue-button`, `.win-restart-button`), game over (`.game-over`:
`.game-over-win-note`, `.restart-game-button`; both texts, `You've reached <target>!`, are written by
`OverlayView`, the markup holds no number), the reusable confirmation
(`.confirm-dialog`: `.confirm-title`, `.confirm-message`, `.confirm-cancel-button` with
`autofocus`, `.confirm-accept-button`; texts filled by `ConfirmDialogView`), and the settings
(`.settings-dialog`: a title, one `.settings-section` per setting — today Board size and Win target, each a
radio group drawn as `.segmented` — and `.settings-close-button` with `autofocus`, see "Settings" below). Dialogs:
`ai/decisions/2026-10-10-native-dialog.md`, `ai/decisions/2026-10-10-confirm-dialog.md`,
`ai/decisions/2026-10-11-settings-dialog-and-storage.md`.

### Header (`.game-header`)

Two rows, as wide as the board: `.game-layout` shrink-wraps to the board and the header
(`width: min-content; min-width: 100%`) adds only its minimum width to that size, so it
takes the board's width and is never narrower than its own content
(`ai/decisions/2026-10-10-header-toolbar.md`).

1. `h1.logo` (`2048` on a gold tile) and `.toolbar`, a flex row of icon buttons. It holds
   `.new-game-button` (a plus icon), `.theme-toggle` (a sun and a moon in the markup,
   CSS shows one; `ai/decisions/2026-10-10-theme-tokens-and-head-script.md`) and
   `.settings-button` (a gear, opens the settings, see "Settings" below).
2. `.score-container` with two `.score-box`es, each a label (`.score-label`) above a
   value. `Score`: `.current-score` (`aria-hidden`), the visually hidden
   `.score-announcement` live region, and the empty `.score-pops` (`aria-hidden`), the
   container of the `+N` pop (`ai/decisions/2026-10-10-score-pop.md`). `High Score`:
   `.high-score` (no live region), `.reset-high-score-button`, an icon button, `hidden`
   while the high score is 0, and `.record-badge`, the `New record!` flag on the top edge of
   the box (`aria-hidden`, `hidden` except for 4 s after a record is beaten;
   `ai/decisions/2026-10-10-new-record-badge.md`). The reset stays here, it is not a
   setting (`ai/decisions/2026-10-11-high-score-reset-stays-in-the-header.md`).

**Adding a toolbar button** (the theme toggle and the settings button are the worked examples):
copy the `New Game`
`<button class="toolbar-button" aria-label="…" title="…">` into `.toolbar` after the
last button, with its own inline SVG (24px, `viewBox="0 0 24 24"`, `currentColor`,
`aria-hidden="true"`, `focusable="false"`), and give it a hook class for `main.js`. No
CSS and no layout change, unless the icon depends on a state (the theme toggle holds two
SVGs and `controls.css` shows one by `data-theme`). Room at 320px (measured): three 44px
buttons next to the logo fit with the header exactly as wide as the board (57px to spare
between the logo and the toolbar); a fourth still fits without a sideways scroll but makes
the header, and so the board's wrapper, 5px wider than the board; a fifth overflows. Icons
are inline SVG, no library (`ai/rules/style.md`).

### Page: the GitHub link and the footer

`body` is a flex column (`min-height: 100dvh`, centred horizontally) with three parts, top to bottom
(`ai/decisions/2026-10-13-footer-and-github-link.md`):

1. **`.github-link`**, first in the DOM: an `<a>` to `https://github.com/serlisovyk/2048`
   (`target="_blank"`, `rel="noopener"`, an `aria-label` and a `title` that say it opens a new tab) with
   the GitHub mark as inline SVG (24px in a 44px target). A flex item with `align-self: flex-end`, so it
   has a **row of its own** at the top right of the page (the page's width, not the board's) and never
   shares a line with the header: that is why it is not a toolbar button and why it cannot overlap at any
   width. It costs 50px of height (44px and a 6px margin that keeps its focus ring off the header). First
   in the DOM = first in `Tab` order = its visual place; the next `Tab` is `New game`. Colours:
   `--icon-muted`, hover `--icon-hover` on `--icon-hover-bg`; the focus ring is the shared one.
2. **`.game-layout`** (`flex-grow: 1`): the header, the board and the footer. The header and the footer
   both have `margin-top: auto`, so free height is split in two equal gaps: above the header and between
   the board and the footer. With room the footer is at the bottom of the page and the game is centred
   between the icon row and the footer (within about 6px of where it was centred before the footer
   existed); with none, both margins are 0 and the layout's `gap` is the footer's distance to the board,
   and the page scrolls.
3. **`.site-footer`**, the last child of `.game-layout`: the text `Serhii Lisovyk · <year>` (muted text
   colour, 13px, centred) under a 1px `--divider` line. It is inside the wrapper so it is as wide as the
   board without knowing the board's width: like the header it has `width: min-content; min-width: 100%`
   and adds only its minimum width to the wrapper. The markup holds the name and an empty
   `.footer-year`; `FooterView.renderYear` writes ` · 2026` into it when the page loads, so the year is
   never stale and a footer without it never shows a dangling dot.

Heights (measured, 4x4 / 5x5 / 3x3): the icon row and the footer add about 90px. At 320x568 everything fits
with no vertical scroll on every size (about 45px / 41px / 63px to spare); at 320x480 the page scrolls by
about 43 / 47 / 25px. The header, the board and their widths are unchanged at every width and size. Both
the link and the footer are outside the dialogs, so `showModal()` makes them inert.

## Theme

- **One carrier:** `<html data-theme="light|dark">`, always set. The inline script in `<head>` sets it
  before the first paint (a saved `'theme'`, else `prefers-color-scheme: light`, else dark); after
  load `ThemeController` owns it. CSS has the dark values on `:root` and one `:root[data-theme='light']`
  block; there is no `prefers-color-scheme` block in the stylesheets. If the script fails the page is dark.
- **Colours only through tokens:** every colour is a custom property in `styles/theme.css` (UI) or
  `styles/tiles.css` (tiles); the other stylesheets read `var(--…)` and nothing else. A new colour needs
  a dark value, a light value (or a deliberate "same in both") and a contrast check in both themes
  (`ai/rules/style.md`).
- **`theme-color`:** two static metas in `index.html` (`#f4efe6` light, `#333333` dark) hold the system
  case from the first parse; `ThemeView.render` then sets both to the `--page-bg` of the theme in force.
  The two hex values in the HTML must equal `--page-bg` of each theme.
- **The reveal:** a View Transition circle from the toggle, in `theme.css`; progressive enhancement
  (`ai/decisions/2026-10-10-view-transitions-progressive-enhancement.md`).
- **Not themed:** `favicon.svg` keeps its own colours (see "Link preview" below), and so do the
  preview images, which show both themes at once.

## Settings

The settings button is on (MY-128 turned it on with the first section, Board size) and the dialog
has two sections, Board size and Win target (MY-129); statistics are MY-130. Why, and the format:
`ai/decisions/2026-10-11-settings-dialog-and-storage.md`; the board size:
`ai/decisions/2026-10-12-board-size-records-and-saved-game.md`; the win target and its choices per size:
`ai/decisions/2026-10-13-win-target-per-board-size.md`.

- **Pieces:** `Settings` (model: values and validation, `SETTING_DEFINITIONS` in `constants.js`),
  `SettingsView` (dialog, button, `Close`), `SettingsController` (load, open, apply a change, ask
  first), all wired in `main.js`. A setting is saved as one flat object under one key (below).
- **A change starts a new game.** Every planned setting does, so `requestChange` asks through
  `ConfirmDialogView` when `GameController.isInProgress`; the settings closes while the question
  is open and reopens on "no". Never two open dialogs.
- **Board size** is the worked example of a setting (the long version is the "Settings" step in
  `ai/skills/feature.md`). `GameController` takes the same `Settings` object as the settings controller
  and reads `boardSize` where a game starts, so the new value is used by the `restart()` that ends
  `requestChange`. A game saved at another size than the setting wins on load. The size is shown by the
  `.segmented` control (a `<span>` per option over a visually hidden radio).
- **Win target** is the worked example of a setting whose choices depend on another: three tiles per board
  size (`WIN_TILES`: 3x3 256 / 512 / 1024, 4x4 1024 / 2048 / 4096, 5x5 2048 / 4096 / 8192), the middle one
  is the default and what a size change returns to. Its definition has `dependsOn: boardSize`, and `Settings`
  keeps the value valid for the size. The same `.segmented` markup is used, but its three radios have no
  fixed values: `SettingsController` hands `SettingsView.render` the choices of the current size every time
  it renders (on `open()` and after a change, because the dialog stays open on a fresh game). `Game` takes the
  tile with the size (`start(size, winTile)`), the saved game stores it and the win texts name it. The target is
  shown nowhere else (not in the header or on the board).
- **Adding a section**:
  1. `constants.js`: add the setting to `SETTING_NAMES` and `SETTING_DEFINITIONS`
     (`{ defaultValue, allowedValues }`), no version bump.
  2. `index.html`: add a `<section class="settings-section">` with an `<h3 id="…">` and a
     `<div role="radiogroup" aria-labelledby="…">` (the heading's id) that holds one
     `<label><input type="radio" name="<setting>" value="<allowed value>"> …</label>` per choice,
     inside `.settings-dialog`, between the title and `Close`. No `aria-labelledby` on the
     `<section>` itself: it would add a second landmark with the group's name (checked in the
     accessibility tree: heading, then a named radio group). No JavaScript is needed to show or
     to change it. For a few exclusive options reuse `.segmented` / `.segment`
     (`<label class="segment"><input class="visually-hidden" type="radio" …><span>…</span></label>`).
  3. Style any new control in `controls.css` / `overlays.css` with tokens only; make the game read
     `Settings.get(name)` where it builds the game (`settingsController.start()` already runs
     before `controller.start()`; `requestChange` ends in `GameController.restart()`, which then
     has to build the new value). If the value is stored with the game, the save wins over a
     disagreeing setting, as the size does.
  4. If its choices depend on another setting (the win target on the size): give the definition
     `dependsOn` and an `allowedValues` map from the other setting's value to the choices (no
     `defaultValue`: the middle choice), list it after that setting, and pass its choices to
     `SettingsView.render` in `SettingsController.#render` (the markup then has as many radios as the
     lists have choices, the labels are the values).
  5. Update this section, the `Storage` section if the format changed, and the docs the issue
     lists.

## Link preview (Open Graph) and the favicon

What a chat or a social network shows for the link, and the tab icon. Why it is a hand-made
PNG with no generator: `ai/decisions/2026-10-12-og-preview-image.md`.

- **Meta tags** (`src/index.html`, after `og:type`): `og:url`, `og:image`, `og:image:type`,
  `og:image:width`, `og:image:height`, `og:image:alt`, `twitter:card` = `summary_large_image`, all
  URLs absolute on `https://2048-xi-three.vercel.app/` (crawlers do not resolve relative ones). No
  `twitter:image` or `twitter:title`: X falls back to `og:*`. A new domain means editing `og:url`
  and `og:image`.
- **Files:** `public/og-image.png` (1200×630, about 105 kB) is copied as it is to `dist/` and served at
  `/og-image.png`; `.github/social-preview.png` (1280×640, about 98 kB) is the same picture for GitHub's
  Social preview, uploaded by hand in the repository settings and never deployed. The `size-limit`
  entries match only `dist/assets/*.js`, `*.css` and `*.woff2`, so the PNGs are outside every budget.
- **The picture:** the background is cut by a straight line from the bottom-left to the top-right corner
  (corner to corner at any size) into the dark page colour (top-left triangle) and the light one
  (bottom-right). Top-left: the header logo scaled up and the tagline `Slide. Merge.` / `Reach 2048.`,
  both entirely inside the dark triangle. Right: a 4x4 board, the only thing the line crosses, cut by the
  same line (dark panel above it, light below). No toolbar, so a change of header buttons does not make it
  stale.
- **How it was made** (nothing of it is in the repo; remake it the same way). One HTML page holding the
  same scene twice, scoped to a wrapper with `theme.css`, `tiles.css` and `board.css` read from the repo
  (selectors `:root` to the wrapper, so the values are the real ones) and Rubik inlined from
  `src/fonts/`: a `light` copy filling the page and a `dark` copy on top, clipped with
  `clip-path: polygon(0 0, 100% 0, 0 100%)`. Logo: `--logo-bg`, `--on-gold`, `--logo-shadow`, Rubik 700
  at 132px, padding 14px 44px, radius 28px. Tagline: Rubik 400 at 48px in `--text`. Board: the game's own
  structure at its largest size (`--cell-size: 100px`, `--cell-gap: 12px`, container and grid padding
  equal to the gap), tiles from `tiles.css` as they are, laid out as a finished game's snake, rows top to
  bottom `· · · 2`, `8 4 2 ·`, `16 32 64 128`, `2048 1024 512 256`. A third copy of just the tiles, not
  clipped and without shadows, is laid over both so the line passes behind the tiles and never through
  one (two clipped copies of a tile leave a hairline along the cut). Rendered in headless Chrome
  (`--headless=new`, `--force-color-profile=srgb`) with `Page.captureScreenshot` at an exact viewport of
  1200×630 and of 1280×640, then re-encoded losslessly with `node:zlib` (RGB, per-row filter search,
  level 9: 125 kB to 105 kB).
- **Remake both PNGs when** the tile palette, the logo gold, a page colour in `theme.css`, or the
  tagline changes. Check the result by reading the corner pixels (top-left `#333333`, bottom-right
  `#f4efe6`) and that the logo and the tagline boxes stay inside the dark triangle.
- **After a deploy:** crawlers cache the card, the file name does not change. Refresh Telegram with
  `@WebpageBot` and LinkedIn with its Post Inspector; opengraph.xyz shows what a crawler reads.
- **Favicon** (`src/favicon.svg`, hashed by Vite, not themed): the dark square (`--page-bg`), the board
  (`#555555`, `--surface-border`) and four tiles, in reading order the 2 tile `#f1ebdb`, the logo gold
  `#edc22e`, the 64 tile `#f0621d` and the 2048 tile `#99007a`: the ramp from cream to the target, four
  colours that stay distinct at 16px. It was `#eee4da`, `#ede0c8`, `#f2b179`, `#edc22e` (the old 2048
  palette, two near-identical creams). A change of the palette is a change here too.

## Storage

| Key (`STORAGE_KEYS`)                                                                         | Value                                                                                  | Written by                                                                                 |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `HIGH_SCORE_PREFIX` + `<size>x<size>` → `'highScore3x3'`, `'highScore4x4'`, `'highScore5x5'` | number, as a string (`0` after a reset); the record of that size                       | `GameController` via `SafeStorage`                                                         |
| `LEGACY_HIGH_SCORE` → `'highScore'`                                                          | the one record before the sizes; moved to the 4x4 key on the first start, then removed | read and removed by `GameController`                                                       |
| `SAVED_GAME` → `'savedGame'`                                                                 | JSON `{ version, size, winTile, board, score, hasWon }`                                | `GameController` via `SafeStorage`                                                         |
| `THEME` → `'theme'`                                                                          | `'light'` or `'dark'`, only after the player used the toggle                           | `ThemeController` via `SafeStorage` (read by it, and by the inline script in `index.html`) |
| `SETTINGS` → `'settings'`                                                                    | JSON `{ version, <name>: <value>, … }`, only after a change                            | `SettingsController` via `SafeStorage`                                                     |

**The one exception to "storage only through `SafeStorage`":** the inline script in `index.html`
reads `THEME` directly (the literal `'theme'`, with a comment pointing at `STORAGE_KEYS.THEME` and
a comment there pointing back), inside `try/catch`, because it runs before any module and so
cannot import `SafeStorage`. It only reads. `ai/decisions/2026-10-10-theme-tokens-and-head-script.md`.

The saved game (`SAVED_GAME_VERSION` = 3: `{ version, size, winTile, board, score, hasWon }`, `size` 3, 4 or
5, `winTile` one of the three choices of that size) is written after every successful move, deleted on game
over, `New Game`, `Restart Game`, and when it fails validation on load — a finished game is never stored. The
model validates the size, the win tile and the board; the controller brings an older save up to date through
`#SAVE_UPGRADES` (1 → 2: no `size` means 4x4, 2 → 3: no `winTile` means the middle choice of the size) and
treats any other version as no save. **A new save version is one more entry in that table plus the bump**
(MY-130's move counter: `3: (saved) => ({ ...saved, version: 4, moves: 0 })`). Format and rules:
`ai/decisions/2026-10-10-saved-game-format.md`, `ai/decisions/2026-10-12-board-size-records-and-saved-game.md`,
`ai/decisions/2026-10-13-win-target-per-board-size.md`.

The settings (`SETTINGS_VERSION` = 1) are one flat object, written only when a setting changes.
The controller checks the version (another one: every default) and `Settings.restore` keeps each
valid field and defaults only the broken ones, so damaged or missing data never stops the game.
Fields are the names in `SETTING_DEFINITIONS` (`boardSize`: 3, 4 or 5, default 4; `winTile`: a choice of the
saved `boardSize`, default the middle one: 512, 2048 or 4096; a `winTile` that does not fit the size costs only
itself). Adding a field with a default needs no version bump (`winTile` did not); changing what an existing field
means or allows does.
`ai/decisions/2026-10-11-settings-dialog-and-storage.md`.
