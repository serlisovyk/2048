## 1. Choices

### The year is filled in the browser, by a tiny view

Options: (a) a view that writes it when the page loads; (b) a Vite `transformIndexHtml` step that
replaces a placeholder at build time; (c) write the year in the markup.

(a) is chosen. A static site built in 2026 would still say 2026 in 2027 under (b) until the next
deploy, which is not "current, automatic"; (c) is the hard-coded year the author does not want; and
(b) edits `vite.config.js`, a repo-wide file that does not run beside other branches. (a) costs one
~12-line class and one line in `main.js`.

`FooterView` (`ui/`, a view) owns the `.footer-year` element and has one method,
`renderYear(year)`. `main.js` finds the element, creates the view and calls
`renderYear(new Date().getFullYear())`: the composition root already hands browser globals to
objects (`matchMedia`, `document.documentElement`), so reading the clock there is the same kind of
wiring and no logic. There is no controller: nothing is decided, nothing is stored.

The markup holds `Serhii Lisovyk` and an empty `<span class="footer-year">`; the view writes
` · 2026` (the separator and the year together). So before the script runs, and if it never does, the
footer reads `Serhii Lisovyk` and never `Serhii Lisovyk ·` with a dangling dot. The year is read once
per page load; a tab left open over midnight on 31 December keeps the old year until a reload, which
is the right amount of precision for a footer.

### The footer is inside `.game-layout`, so it is as wide as the board without knowing it

The board's width is not known to CSS outside the wrapper (`.game-layout` shrink-wraps to it).
Repeating the cell arithmetic in a footer rule was rejected for the header and is rejected here, and
a width from JS is a second source. So the footer is the last child of `.game-layout` and takes
`width: min-content; min-width: 100%`, as the header does: it contributes only its minimum width to
the wrapper's size, so it never widens the board, and it stretches to the board's width. The divider
is its `border-top`. It is a `<footer>` in a `div`, which is still the page's `contentinfo`
(landmark rules exclude only `article`, `aside`, `main`, `nav` and `section` ancestors).

### Pinned to the bottom with room, after the board without it

`body` is already a flex column with `min-height: 100dvh`. `.game-layout` gets `flex-grow: 1`, so it
fills what the icon row leaves, and inside it the header and the footer both get `margin-top: auto`.
The free space is split equally between the two auto margins: the same amount above the header and
between the board and the footer, which is the footer at the bottom and the game centred in what is
left. Without free space both margins are 0 and the flex `gap` (`--header-gap`) is the footer's
distance to the board, so on a short screen the footer follows the board. The footer needs no
`position`, no `vh` arithmetic and no breakpoint. `justify-content: center` on `body` has nothing
left to do and is removed (the layout fills the column).

Rejected: `position: fixed` / `absolute` footer (it covers the board on short screens), a CSS grid
body with spacer rows (the footer would then be a body child and could not take the board's width
without a second source), and a sticky footer with a fixed height.

### The GitHub icon is a row of its own, first in the page

"At the very top right" and "never overlaps" cannot both be met by an out-of-flow corner icon: at
375px the board leaves 32px on each side, less than the 44px target, so a corner icon would sit on
the header, and on a short screen the header starts at the top padding. So the icon is a flex item
of `body` with `align-self: flex-end`: its own row, right-aligned in the page (not in the board's
width), above the game. It costs 44px + 6px of height on a short screen and nothing on a tall one
(the layout centres the game in what remains), and it cannot overlap anything at any width because
nothing else is in its row. Rejected: a corner icon out of flow with a breakpoint for wide
screens (two modes, one of them a guess about the board's width, to save 50px on laptop-height
windows); a fourth toolbar button (the author excluded it; it makes the header 5px wider than the
board at 320px); putting it in the logo row.

It is first in the DOM, so reading order, `Tab` order and visual order agree. The alternative, last
in the DOM and placed at the top with CSS `order`, would make the focus jump against the picture.

The link looks like the quiet reset-high-score icon, not a bordered toolbar button: `--icon-muted`,
`--icon-hover` and `--icon-hover-bg` already exist and are contrast-checked, so there is no new
colour for it.

### Links get the shared focus ring

`base.css` draws the ring for `button` only. The rule becomes `button, a`, with the same three
declarations and the same `:focus-visible` flip, so the ring (its width, offset and token) is one
thing. The link has no `transition: all`, so the base-rule trick that stops the ring from animating
in is not needed but kept for the same rule to serve both. The ring (3px + 3px offset) reaches 6px
outside the 44px box, so the link keeps a 6px bottom margin and the header's top edge is never under
it.

### One new token, for the divider

`--surface-border` is `#555` on `#333` (1.7:1) in the dark theme and `#ddd3c2` on `#f4efe6` (1.3:1) in
the light one, too faint for a line that has to be seen in both. A new token `--divider` has its own
values (about 2:1 against the page in each theme; a decorative line has no contrast requirement, the
value is for being seen). The footer text uses `--text-muted`, already checked for text on the page
background.
