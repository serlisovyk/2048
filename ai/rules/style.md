# Style Rules

## General

- Prefer readable HTML, CSS, and JavaScript over clever tricks.
- Keep changes close to the feature or file section they affect.
- Avoid unnecessary comments. Add comments only when they explain non-obvious
  reasoning.
- Use existing naming and spacing patterns before introducing new ones.

## HTML

- Use semantic elements for major regions.
- Use buttons for actions.
- Give interactive controls clear accessible names when visible text is not
  enough.
- Icons are inline SVG written in the markup: `viewBox`, `stroke="currentColor"` (or
  `fill`), `aria-hidden="true"`, `focusable="false"`. No icon font, icon library,
  image file, or `<use>` sprite. A button that holds only an icon has an `aria-label`
  and a `title` with the same text.
- A value that changes during play and matters to a screen-reader user (the score)
  gets a live region: a visually hidden `<span aria-live="polite" aria-atomic="true">`
  that the owning view fills after a short debounce (the delay is in
  `src/scripts/constants.js`). The visible number next to it is `aria-hidden="true"`,
  so browse mode reads the value once. Always `polite`, never `assertive`; no live
  region on a value that is not worth announcing (the high score).
- Text that is only for assistive technology uses the `.visually-hidden` class, not
  `display: none` or `hidden`, which also hide it from screen readers.
- Keep metadata concise and aligned with the visible game.
- Keep game markup compact. The board cells are generated by JavaScript.

## CSS

- Keep plain CSS. Do not introduce Less, Sass, or CSS-in-JS unless explicitly
  requested.
- Keep CSS split by responsibility through the files imported in
  `src/styles/main.css`.
- Keep responsive rules near the layout or component they affect.
- Keep reduced-motion rules in `src/styles/motion.css`.
- Use CSS custom properties for values that are shared inside a component.
- When CSS needs a number defined in `src/scripts/constants.js` (board size,
  durations), the owning view sets it as a custom property and the CSS reads it with
  a fallback: `var(--board-size, 4)`.
- Focus: one generic `button:focus-visible` rule in `base.css` draws the ring for
  every button, in the colour of `--focus-ring-color`. Do not add per-button focus
  styles or `outline: none` / `outline: 0` on a button; a new button gets the ring
  without any CSS. The ring is an `outline`, not a `box-shadow`: the buttons' hover
  rules set their own `box-shadow` and would hide it.
- The ring's width, gap, and colour sit on the base `button` rule and only the
  `outline-style` flips on `:focus-visible`, because buttons use `transition: all`
  and would otherwise animate the ring in.
- An element focused only from script (`tabindex="-1"`, like the board) gets
  `:focus-visible { outline: none }` instead of a ring.
- Avoid one-off visual effects that do not improve the game UI.

## JavaScript

- Follow `ai/rules/oop.md`: ES classes, one per file, private state, layers,
  constructor-injected dependencies.
- Class files are PascalCase (`GridView.js`); `main.js` and `constants.js` are the
  only camelCase modules. Named exports only.
- Imports include the `.js` extension.
- Keep game logic simple and event-driven.
- Keep movement rules deterministic except for new tile placement.
- Do not expose game state on `window`.
- Do not add utility-heavy abstractions for one-use logic.

## Formatting

- Use Prettier.
- Use single quotes where Prettier applies them.
- Do not use semicolons in JavaScript config files.
- Keep `printWidth` at `85`.
- Use `yarn format` to apply formatting.
