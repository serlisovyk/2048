# Style Rules

## General

- Prefer readable HTML, CSS, and JavaScript over clever tricks.
- Keep changes close to the feature or file section they affect.
- Avoid unnecessary comments. Add comments only when they explain non-obvious
  reasoning.
- Use existing naming and spacing patterns before introducing new ones.

## HTML

- Use semantic elements for major regions.
- Use buttons for actions.
- Give interactive controls clear accessible names when visible text is not
  enough.
- Icons are inline SVG written in the markup: `viewBox`, `stroke="currentColor"` (or
  `fill`), `aria-hidden="true"`, `focusable="false"`. No icon font, icon library,
  image file, or `<use>` sprite. A button that holds only an icon has an `aria-label`
  and a `title` with the same text.
- A value that changes during play and matters to a screen-reader user (the score)
  gets a live region: a visually hidden `<span aria-live="polite" aria-atomic="true">`
  that the owning view fills after a short debounce (the delay is in
  `src/scripts/constants.js`). The visible number next to it is `aria-hidden="true"`,
  so browse mode reads the value once. Always `polite`, never `assertive`; no live
  region on a value that is not worth announcing (the high score).
- A decoration that repeats a value the live region already announces (the score pop,
  `+N`) sits in its own container with `aria-hidden="true"`, outside the live region and
  outside the visible value, so it is never read and never changes the value's text.
- A decoration whose meaning must be heard (the `New record!` badge) is `aria-hidden`
  too and has no live region of its own: its view keeps a pending flag, and the one
  announcement of the score that follows reads `New record! <score>` (the badge's own
  text, written once). Never a second live region for the same event.
- Text that is only for assistive technology uses the `.visually-hidden` class, not
  `display: none` or `hidden`, which also hide it from screen readers.
- Keep metadata concise and aligned with the visible game.
- Keep game markup compact. The board cells are generated by JavaScript.

## CSS

- Keep plain CSS. Do not introduce Less, Sass, or CSS-in-JS unless explicitly
  requested.
- Keep CSS split by responsibility through the files imported in
  `src/styles/main.css`.
- Keep responsive rules near the layout or component they affect.
- Keep reduced-motion rules in `src/styles/motion.css`.
- The reduced-motion rule there sets every `animation-duration` to 0.01ms with
  `!important`. An animation that the player must still see (the score pop) would be
  gone at once, so it gets its own override in `motion.css`: no movement (the rise is a
  custom property, `--score-pop-rise: 0px`) and its duration restored with `!important`;
  the more specific selector beats `*`. Every other animation stays instant. The record
  badge is the second case and is static: its override restores the duration and swaps in
  keyframes that change nothing (`record-badge-static`), because `animationend` still has
  to fire to remove it.
- A transient element that JS creates (the score pop) removes itself on `animationend`
  and takes its duration from a CSS custom property, so JS holds no timer for it. One that
  is a `hidden` element in the markup (the record badge) is shown by clearing `hidden`,
  which starts its animation afresh each time, and hidden again on `animationend`; it sets
  no `display`, so `hidden` keeps working, and it floats out of the layout like the pop.
- Use CSS custom properties for values that are shared inside a component.
- When CSS needs a number defined in `src/scripts/constants.js` (board size,
  durations), the owning view sets it as a custom property and the CSS reads it with
  a fallback: `var(--board-size, 4)`.
- Focus: one generic `button:focus-visible` rule in `base.css` draws the ring for
  every button, in the colour of `--focus-ring-color`. Do not add per-button focus
  styles or `outline: none` / `outline: 0` on a button; a new button gets the ring
  without any CSS. The ring is an `outline`, not a `box-shadow`: the buttons' hover
  rules set their own `box-shadow` and would hide it.
- The ring's width, gap, and colour sit on the base `button` rule and only the
  `outline-style` flips on `:focus-visible`, because buttons use `transition: all`
  and would otherwise animate the ring in.
- An element focused only from script (`tabindex="-1"`, like the board) gets
  `:focus-visible { outline: none }` instead of a ring.
- Tile colours live in `src/styles/tiles.css` and nowhere else. Every colour is a
  custom property on `:root` (`--tile-<value>`, `--tile-fallback`, `--tile-text-dark`,
  `--tile-text-light`, `--tile-sheen`, `--tile-2048-glow`) and the rules only read
  tokens, so a theme overrides the tokens and touches no selector. `board.css` keeps
  only the structure of a tile (weight, shadow, `transition`).
- The base rule `.grid-cell[data-value]` is the first rule in `tiles.css` and is the
  fallback for every value that has no rule of its own (32768 and up). The per-value
  rules `[data-value='N']` come after it: same specificity, so they win by order. Never
  write the fallback as a `:not()` chain of the values that have a rule.
- Adding a tile value is a token plus one rule after the base rule, in value order:
  `background-color`, `color` (`--tile-text-dark` or `--tile-text-light`) and
  `font-size`. Size follows the digit count, each as a `clamp()`: 1-2 digits 40px,
  3 digits 35px, 4 digits 30px, 5 digits 25px, the fallback 20px (6 digits).
- Tile colours are two ramps in one logic: 2 to 2048 run from cream through amber, red
  and magenta, 4096 and up restart in lavender and run to deep blue. A new colour keeps
  that order (lightness falls, chroma rises, hue keeps turning) and stays clearly
  different from its neighbours.
- The tile text must reach 3:1 against **both** ends of the gradient: the base colour
  and the base colour blended 14% with white (the light end of `--tile-sheen`). Use dark
  text where the tile is light, light text where it is dark, and compute the ratio with
  the WCAG formula, because axe does not check gradients.
- Typography lives in `src/styles/base.css`: one family, set once on `body`
  (`'Rubik', Arial, sans-serif`) and inherited by everything else
  (buttons through `font: inherit`). Do not set `font-family` on other elements. The UI
  uses two weights, normal (400) and `bold` (700); `font-variant-numeric: tabular-nums`
  is set once on `body`, so every number, including one added later, keeps its width as
  it changes. Do not repeat it per element.
- `body` pins `line-height: 1.15` (Arial's `normal`) so box heights do not depend on
  which face is active; elements that set their own `line-height` keep it.
- The font is the `@font-face` at the top of `base.css` (`font-display: swap`), with
  Arial as the fallback in the stack. While the font loads on a first, uncached visit the
  logo and the numbers are set in Arial and change width a little when Rubik arrives (the
  logo by about 15px); that is accepted, there is no metric-adjusted fallback face. A new
  weight, an italic, another script or another face needs a decision record
  (`ai/decisions/2026-10-10-self-hosted-font.md`).
- Avoid one-off visual effects that do not improve the game UI.

## JavaScript

- Follow `ai/rules/oop.md`: ES classes, one per file, private state, layers,
  constructor-injected dependencies.
- Class files are PascalCase (`GridView.js`); `main.js` and `constants.js` are the
  only camelCase modules. Named exports only.
- Imports include the `.js` extension.
- Keep game logic simple and event-driven.
- Keep movement rules deterministic except for new tile placement.
- Do not expose game state on `window`.
- Do not add utility-heavy abstractions for one-use logic.

## Formatting

- Use Prettier.
- Use single quotes where Prettier applies them.
- Do not use semicolons in JavaScript config files.
- Keep `printWidth` at `85`.
- Use `yarn format` to apply formatting.
