## 1. What is wrong today

- One dark theme. 40 lines of colour literals in six files (`base`, `layout`, `header`,
  `board`, `overlays`, `controls`; the tile shadow in `board.css` is one of them), plus
  `#333333` in the `theme-color` meta. Only the tile colours (MY-122) and the focus ring are
  tokens already.
- `prefers-color-scheme` is ignored, and nothing is stored about it.
- Default button text is the browser's `ButtonText` (black), not a colour the CSS chose. A
  theme that sets `color-scheme: dark` would turn it white on the white dialog buttons, so
  every colour has to be explicit.

## 2. How the theme is chosen (one picture)

```text
head script (before first paint)      main.js, after DOMContentLoaded
  stored = localStorage 'theme'         ThemeController.start()
  theme  = stored if light/dark           same rule, through SafeStorage
           else system (light/dark)       renders the theme (idempotent) + follows the system
  html[data-theme] = theme                ThemeView.render: attribute, label, icon, theme-color
                                        toggle click -> store -> ThemeView.transitionTo
```

`<html data-theme="light|dark">` is the single carrier of the theme and is always set. CSS has
the dark values on `:root` and one override block on `:root[data-theme='light']`. The CSS has
no `prefers-color-scheme` block: that would repeat the light block and give two places that
decide the theme. JS decides once, and the page is not playable without JS anyway; if the head
script ever fails, the fallback is today's dark look.

## 8. Applying the theme before the first paint

An inline classic `<script>` in `<head>`, before the module script, in an IIFE so it leaks no
globals. Storage is read inside `try/catch` and the rest runs outside it, so blocked storage
still gets the system theme:

```html
<script>
  ;(() => {
    let stored = null

    try {
      // The key mirrors STORAGE_KEYS.THEME in src/scripts/constants.js.
      stored = localStorage.getItem('theme')
    } catch {
      // Storage is blocked: fall back to the system setting.
    }

    const theme =
      stored === 'light' || stored === 'dark'
        ? stored
        : matchMedia('(prefers-color-scheme: light)').matches
          ? 'light'
          : 'dark'

    document.documentElement.dataset.theme = theme
  })()
</script>
```

- **Default.** `prefers-color-scheme: light` matches only when the system asks for light, so a
  browser that does not know the feature gets today's dark look.
- **`minify-html`.** I ran the repo's exact `html-minifier-terser` options over this script.
  The optional `catch {}` binding survives and the output is one line of about 205 bytes; the
  minified script, run against seven stored/system/blocked-storage combinations, picks the
  right theme in all of them. `removeScriptTypeAttributes` only strips `text/javascript`, and
  this script has no `type`.
- **Vite, measured on a throwaway copy of the app** (outside the repo) with this script: the
  real `vite build` leaves the classic inline script alone, minifies it, and puts it in
  `<head>` before the module script and the render-blocking `<link rel="stylesheet">` that
  the build adds, so in the production build nothing paints before the attribute is set. The
  dev server serves the same script. (The throwaway copy also carried the optional key
  plugin the author did not choose; the script itself is the same either way.) `index.html`
  grows by about 0.2 kB (2.93 to 3.15). The real `yarn build` output is re-read at the end.
- **Dev server.** There the page has no stylesheet link: `main.js` imports the CSS, so the
  first frame is unstyled (white) before `main.js` runs, in any theme. That already happens
  today and is not new; I will describe it plainly in the report and not engineer around it.
- **The storage key is a literal in the script, with a comment on both sides** (the author's
  answer 4; a Vite plugin that substituted it from `constants.js` was proposed and declined, as
  a build step for one string): `STORAGE_KEYS.THEME` lives in `constants.js` with a comment
  that the inline script in `index.html` reads the same key, and the script has a comment that
  points back. The values `light` and `dark` are literals in the script too: they are the
  `data-theme` contract of the CSS, like class names. If the key is ever renamed and the
  script is forgotten, the page loads in the wrong theme for a frame and `ThemeController`
  corrects it, so it degrades into a flash, not a break.
- **The exception, recorded openly.** This script is the one place that reads `localStorage`
  without `SafeStorage`: it runs before any module exists, so it cannot import it. It is
  guarded by `try/catch` and only reads. It is written down in the new decision record, in
  `ai/rules/oop.md` (Storage row), in the "Avoid" list of `ai/skills/feature.md` and in
  `ai/map.md`. Every other read and write, including the one on toggle, goes through
  `SafeStorage`.
- **`theme-color`.** `index.html` carries two static metas, `media="(prefers-color-scheme:
light)"` with `#f4efe6` and `(prefers-color-scheme: dark)` with `#333333`, so the system case
  is right from the first parse without JS. `ThemeView.render` then sets the `content` of both
  to the page colour of the theme in force, read from the `--page-bg` token with
  `getComputedStyle`, so no JS file repeats a hex value and the bar cannot drift from the page.
  The two HTML values and the two `--page-bg` values are the one duplication that cannot be
  removed (HTML cannot read CSS); `ai/rules/assets-performance.md` will say they must match.
  Only when the saved choice differs from the system is the bar briefly the system colour until
  `main.js` runs. Putting the colours into the head script would close that gap; I did not,
  to avoid hex literals in JS (question 6).
- **`color-scheme`** is set in `theme.css` with the tokens, so scrollbars follow the theme.

## 9. The OOP design

Two small classes, split the way `GameController` and the views are. `GameController` is not
touched: the theme is not game state.

| Piece                                      | Layer       | Owns                                                                                                                                                          |
| ------------------------------------------ | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `THEMES`, `STORAGE_KEYS.THEME` (`'theme'`) | constants   | the two theme names and the storage key; `THEMES` is a frozen object like `DIRECTIONS`                                                                        |
| `SafeStorage.getString(key)`               | storage     | new method: the stored string or `null`, never throws (the existing getters are number and JSON only)                                                         |
| `ui/ThemeView.js`                          | view        | `data-theme` on `<html>`, the toggle button (label, title), both `theme-color` metas, the circle reveal                                                       |
| `ThemeController.js`                       | controller  | the current theme, whether it was chosen by the player, persistence, following the system                                                                     |
| `main.js`                                  | composition | finds `document.documentElement`, `.theme-toggle`, the two metas, creates `matchMedia` queries, wires `view.onToggle` to `controller.toggle`, calls `start()` |

`ThemeView`:

- `onToggle(handler)` — the click. `render(theme)` — instant: sets the attribute, the button's
  `aria-label` and `title` (`Switch to light theme` in the dark theme, `Switch to dark theme`
  in the light one), and both metas. It is idempotent, so calling it on start with the value
  the head script already set changes nothing.
- `transitionTo(theme)` — the same render, wrapped in `document.startViewTransition` when the
  API exists and `prefers-reduced-motion` is not `reduce`; otherwise it calls `render` at once.
  Before starting, it writes the button's centre and the distance to the farthest window corner
  as `--theme-reveal-x`, `--theme-reveal-y` and `--theme-reveal-radius` on `<html>`: numbers
  passed to CSS, the one allowed kind of inline style
  (`2026-10-10-css-custom-properties-from-js.md`). It uses the button's rectangle, not the click
  event, so a keyboard activation works. `transition.ready` gets a `.catch(() => {})`, because a
  transition replaced by a newer one rejects it.
- The reduced-motion `MediaQueryList` is a constructor dependency, so the class never reaches
  for `window`.

`ThemeController` (the system query is a constructor dependency too):

- `start()` reads the choice through `storage.getString`, falls back to the system query, calls
  `view.render`, and subscribes to the query's `change`.
- `toggle()` flips the theme, remembers that the player chose, stores it with
  `storage.setValue`, and calls `view.transitionTo`.
- A system `change` while the player has not chosen calls `view.render` (instant, no circle:
  the player did not click anything).
- State is in private fields; the head script and the controller use the same rule, and if they
  ever disagree the controller wins after load.

## 10. The reveal, and the edge cases from the issue

CSS in `theme.css`, no timer in JS:

```css
::view-transition-old(root),
::view-transition-new(root) {
  animation: none;
  mix-blend-mode: normal;
}

::view-transition-new(root) {
  animation: theme-reveal var(--theme-reveal-duration) ease-in-out;
}

@keyframes theme-reveal {
  from {
    clip-path: circle(0 at var(--theme-reveal-x) var(--theme-reveal-y));
  }
  to {
    clip-path: circle(
      var(--theme-reveal-radius) at var(--theme-reveal-x) var(--theme-reveal-y)
    );
  }
}
```

I checked this on the prototype in Chrome 154: `startViewTransition` runs, the custom
properties resolve inside the pseudo-element keyframes (the circle grows from the button's
centre, 1000px and 320px), `ready` and `finished` both resolve, and with `prefers-reduced-motion:
reduce` emulated no transition is created and the theme applies at once. A browser without the
API is checked by deleting `document.startViewTransition` before load. This is a progressive
enhancement because View Transitions are not in the "widely available" baseline that Vite's
default target means (`no-legacy-plugin`); the instant switch is the base behaviour. A decision
record says so.

- **Mid-animation.** Tiles animate with CSS (`pop-in`, `merge-scale`) and the pop with its own
  animation; neither depends on a colour. The new view of a View Transition is live, so they
  keep running; `animationend` still fires. `transition: all` on tiles and buttons makes their
  colours fade over 0.1 to 0.3s as the tokens change. Inside the reveal that is invisible; on
  the instant path it is a short fade of those elements only. I will look at it and add
  nothing unless it shows. Keyboard
  moves keep working during the ~0.5s. Pointer events go to the transition overlay in that
  window, so a click or swipe that starts there is lost; accepted and in the spec.
- **A modal dialog open.** The toggle is inert behind a modal, so a user cannot start a switch
  then. A system-driven change can, and it is an instant token swap: the dialog and its
  `::backdrop` read tokens, so they update in place. Checked on the real build.
- **Two quick switches.** The second `startViewTransition` replaces the first, whose `ready`
  rejects (caught). Each update callback renders its own theme and they run in order, so the
  last one wins. Storage was written for each, the last one is what stays.
