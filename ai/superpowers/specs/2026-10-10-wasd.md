# MY-118 — WASD controls (spec)

Issue: MY-118 · Branch: `my-118-wasd` · Plan: `ai/superpowers/plans/2026-10-10-wasd.md`

## Goal

Move the tiles with **W A S D** as well as the arrow keys, on any keyboard layout,
without stealing browser shortcuts or typing from the user.

## Behavior

### Keys

A key is recognised by its physical position (`event.code`), not by the character it
produces (`event.key`). The same mechanism serves the arrows and WASD.

| `event.code` | Key           | Direction |
| ------------ | ------------- | --------- |
| `ArrowUp`    | ↑             | up        |
| `ArrowLeft`  | ←             | left      |
| `ArrowDown`  | ↓             | down      |
| `ArrowRight` | →             | right     |
| `KeyW`       | W (Russian ц) | up        |
| `KeyA`       | A (Russian ф) | left      |
| `KeyS`       | S (Russian ы) | down      |
| `KeyD`       | D (Russian в) | right     |

- Works on the English and the Russian layout alike, with or without Caps Lock.
- The physical-position trade-off: on a layout that moves the letters (AZERTY,
  Dvorak) the keys that move tiles are the ones in the QWERTY WASD positions, which
  is what players of other games expect.
- Everything else (other letters, digits, Tab, Enter, Space, Escape, F-keys) is left
  alone: no `preventDefault`, no move.

### Keystrokes the game does not take

A keydown that would be a direction key is **ignored completely** — not
`preventDefault`-ed, no move requested — when:

1. **Ctrl, Meta (Cmd / Win) or Alt is held.** `Ctrl+W`, `Ctrl+S`, `Cmd+A`, `Alt+←`
   and the like keep their browser meaning. This applies to the arrows too, so
   `Alt+←` goes back in history instead of moving tiles. **Shift is not a modifier
   here** — `Shift+W` or `Shift+↑` still moves, as `Shift+↑` did before.
2. **The event comes from a form field:** `input`, `textarea`, `select`, or a
   `contenteditable` element — the user is typing or choosing, and the arrows move
   the caret or the option.
3. **The event comes from inside an open dialog:** a native `<dialog open>` or an
   element with `role="dialog"`. Today's win and game-over overlays are
   `<div role="dialog" aria-modal="true">` and take focus when they appear
   (`OverlayView` focuses their button), so the keys act on the dialog, not on the
   board behind it.

Buttons are not form fields for this purpose: after clicking **New Game**, focus
stays on the button and the arrows and WASD must keep working.

### Unchanged

- Plain arrows move the tiles exactly as before; swipes are untouched.
- `GameController.requestMove` stays the single movement guard (cooldown, pause after
  a win, game over). While the win or game-over overlay is shown the board does not
  move, whatever the focus is — the dialog check above is an extra layer, not a
  replacement. Holding a key repeats moves at the controller's cooldown rate, as now.
- Nothing is added to the page: no on-screen hint for the new keys (the controls are
  listed in `README.md`).

### Known consequence

Events carrying only `key` (no `code`) — some virtual keyboards, remote desktops,
synthetic events from test tools — no longer move the board. This is the cost of
having one mechanism, as the issue asks.

## Acceptance (from the issue)

- WASD moves the tiles on the English and on the Russian layout.
- `Ctrl+W`, `Ctrl+S`, `Cmd+A` and similar are not intercepted.
- The arrows work as before.
- Inside an open modal, WASD and the arrows do not move the board.
- `README.md` describes the controls; `ai/map.md` describes the input module.

## Out of scope

- Other hotkeys (`N` for a new game is a rejected idea —
  `ai/decisions/2026-10-10-rejected-features.md`), `Escape`, a shortcuts help.
- Changing the overlays to native `<dialog>`, or any `GameController` / model /
  storage change.
- Remapping keys in a settings screen.
